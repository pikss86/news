## Purpose

Предоставляет оператору закрытую административную страницу для безопасной первоначальной настройки, изменения всех параметров сервиса и наблюдения за состоянием их применения.

## ADDED Requirements

### Requirement: Полный каталог параметров сервиса

Система SHALL позволять через административную страницу настраивать все параметры collector, разделённые на Telegram, PostgreSQL, TDLib, media, журналирование и устойчивость подключений.

#### Scenario: Первоначальная настройка

- **GIVEN** постоянная конфигурация ещё не создана
- **AND** Telegram и PostgreSQL параметры не заданы в `.env`
- **WHEN** оператор открывает административную страницу
- **THEN** страница показывает все обязательные и необязательные параметры с описаниями
- **AND** явно отмечает обязательные поля и значения по умолчанию
- **AND** collector не запускается до сохранения полной валидной конфигурации

#### Scenario: Просмотр существующей конфигурации

- **GIVEN** настройки ранее сохранены
- **WHEN** авторизованный оператор открывает страницу
- **THEN** он видит текущие несекретные значения и состояние применения каждого раздела
- **AND** секретные значения отображаются только как признак наличия без раскрытия содержимого

### Requirement: Автоматический локальный bootstrap

Система SHALL создавать необходимые внутренние database credentials и ключ шифрования settings store автоматически при чистом первом запуске и SHALL сохранять их в постоянном локальном хранилище с ограниченными правами.

#### Scenario: Чистая установка

- **GIVEN** persistent volumes ещё не содержат bootstrap secrets
- **WHEN** стандартный контейнерный стек запускается
- **THEN** необходимые случайные значения создаются до запуска PostgreSQL и панели
- **AND** значения не выводятся в HTML, application logs или Git-tracked файлы
- **AND** повторный запуск использует те же значения

#### Scenario: Bootstrap secret повреждён

- **GIVEN** обязательный внутренний secret отсутствует или имеет неверный формат после инициализации
- **WHEN** зависимый компонент запускается
- **THEN** компонент завершается в безопасном состоянии
- **AND** панель или журнал показывает recovery-инструкцию без генерации несовместимой замены поверх существующих данных

### Requirement: Безопасное изменение секретов

Система SHALL принимать новые секреты, SHALL хранить их зашифрованными и SHALL NOT возвращать сохранённое значение клиенту после приёма.

#### Scenario: Секрет оставлен без изменения

- **GIVEN** секрет уже сохранён
- **WHEN** оператор отправляет форму без нового значения этого секрета
- **THEN** прежнее значение сохраняется
- **AND** не передаётся в HTML или ответе API

#### Scenario: Секрет заменяется

- **GIVEN** авторизованный оператор ввёл новое секретное значение
- **WHEN** валидная форма сохраняется
- **THEN** новое значение сохраняется в зашифрованном виде
- **AND** последующий ответ сообщает только об успешной замене

#### Scenario: Корневой ключ недоступен

- **GIVEN** хранилище содержит зашифрованные настройки
- **AND** правильный bootstrap-ключ недоступен
- **WHEN** сервис пытается загрузить конфигурацию
- **THEN** collector не запускается с пустыми или повреждёнными секретами
- **AND** панель показывает безопасную ошибку восстановления без раскрытия ciphertext

### Requirement: Атомарная валидация настроек

Система SHALL проверять типы, диапазоны, обязательность и согласованность всего отправленного набора до изменения действующей конфигурации.

#### Scenario: Форма корректна

- **GIVEN** оператор заполнил допустимые значения
- **WHEN** форма отправлена
- **THEN** весь набор сохраняется одной новой draft-ревизией
- **AND** collector не запускается и действующая конфигурация не меняется только из-за сохранения draft
- **AND** страница предлагает выполнить проверки

#### Scenario: Одно значение некорректно

- **GIVEN** хотя бы один параметр не проходит проверку
- **WHEN** форма отправлена
- **THEN** новая конфигурация не становится действующей
- **AND** страница показывает ошибку возле соответствующего поля
- **AND** ранее действовавшая конфигурация сохраняется полностью

#### Scenario: PostgreSQL URL не согласован с составными полями

- **GIVEN** оператор задаёт противоречащие друг другу параметры подключения PostgreSQL
- **WHEN** форма проверяется
- **THEN** сохранение отклоняется с объяснением конфликта

### Requirement: Версионирование конфигурации

Система SHALL сохранять последовательные draft и active ревизии настроек без секретов в открытом виде и SHALL позволять установить предыдущую валидную ревизию как новый draft.

#### Scenario: Настройки изменены

- **GIVEN** существует действующая конфигурация
- **WHEN** оператор сохраняет отличающийся валидный набор
- **THEN** создаётся новая draft-ревизия с временем и перечнем изменённых полей
- **AND** предыдущая ревизия не перезаписывается

#### Scenario: Оператор выполняет откат

- **GIVEN** доступна предыдущая валидная ревизия
- **WHEN** оператор подтверждает откат
- **THEN** её значения копируются в новую draft-ревизию
- **AND** событие отката фиксируется в журнале конфигурации
- **AND** сбор не перезапускается до явного подтверждения оператора

### Requirement: Административная аутентификация

Система SHALL требовать административную аутентификацию перед доступом к настройкам и состоянию сервиса.

#### Scenario: Первое открытие панели

- **GIVEN** административный пароль ещё не установлен
- **WHEN** оператор открывает панель
- **THEN** ему предлагается создать пароль администратора
- **AND** пароль сохраняется только как стойкий односторонний хеш

#### Scenario: Неавторизованный запрос

- **GIVEN** клиент не имеет действующей административной сессии
- **WHEN** он запрашивает настройки или состояние
- **THEN** доступ к данным отклоняется

#### Scenario: Успешный вход

- **GIVEN** оператор предоставил правильный пароль
- **WHEN** вход выполнен
- **THEN** создаётся ограниченная по времени сессия с HttpOnly и SameSite=Strict cookie
- **AND** секреты конфигурации не помещаются в cookie

#### Scenario: Повторные неверные пароли

- **GIVEN** клиент несколько раз подряд отправляет неверный пароль
- **WHEN** превышен допустимый темп попыток входа
- **THEN** последующие попытки временно ограничиваются для этого адреса
- **AND** журнал не содержит введённых паролей

### Requirement: Защита изменяющих запросов

Система SHALL принимать изменение настроек, пароля, откат и завершение сессии только с действующей сессией и непредсказуемым CSRF-токеном.

#### Scenario: CSRF-токен отсутствует или неверен

- **GIVEN** запрос пытается изменить состояние
- **WHEN** корректный CSRF-токен отсутствует
- **THEN** запрос отклоняется без изменения конфигурации

### Requirement: Состояние сервиса

Система SHALL показывать авторизованному оператору состояние конфигурации и collector без раскрытия секретов.

#### Scenario: Collector работает

- **GIVEN** collector успешно использует текущую ревизию
- **WHEN** оператор открывает страницу состояния
- **THEN** страница показывает состояние работы, номера draft/active/applied ревизий и время последнего успешного запуска
- **AND** отдельно показывает PostgreSQL, migrations, TDLib, Telegram authorization, media storage и время последнего принятого update

#### Scenario: Collector не запустился

- **GIVEN** последняя попытка запуска завершилась ошибкой
- **WHEN** оператор открывает страницу состояния
- **THEN** отображается безопасное диагностическое сообщение и категория сбоя
- **AND** Telegram, PostgreSQL и административные секреты маскируются

### Requirement: Диагностические проверки до запуска

Система SHALL позволять проверить draft-конфигурацию до её активации и SHALL показывать отдельный результат каждого обязательного компонента.

#### Scenario: Выполняется проверка PostgreSQL

- **GIVEN** draft содержит database configuration
- **WHEN** оператор запускает проверку
- **THEN** система проверяет установление соединения, выполнение безопасного запроса и состояние migrations
- **AND** не изменяет ingestion-данные

#### Scenario: Выполняется проверка TDLib и storage

- **GIVEN** draft содержит TDLib configuration
- **WHEN** оператор запускает проверку
- **THEN** система проверяет загрузку TDLib, доступность и запись в необходимые каталоги и доступное дисковое пространство

#### Scenario: Обязательная проверка неуспешна

- **GIVEN** хотя бы одна обязательная проверка завершилась ошибкой
- **WHEN** оператор просматривает результат
- **THEN** каждый компонент имеет отдельный статус и безопасное диагностическое сообщение
- **AND** действие запуска сбора остаётся недоступным

#### Scenario: Все обязательные проверки успешны

- **GIVEN** PostgreSQL, migrations, TDLib, storage и Telegram authorization подтверждены для текущего draft
- **WHEN** оператор просматривает результат
- **THEN** страница разрешает активировать эту ревизию и запустить сбор

### Requirement: Явное управление сбором

Система SHALL предоставлять авторизованному оператору отдельные действия запуска, остановки и перезапуска collector.

#### Scenario: Запуск после проверок

- **GIVEN** текущий draft прошёл все обязательные проверки
- **AND** Telegram сессия авторизована
- **WHEN** оператор нажимает «Сохранить и запустить сбор»
- **THEN** draft становится active revision
- **AND** supervisor получает ограниченную команду запуска
- **AND** страница показывает переход collector через starting в running либо error

#### Scenario: Остановка сбора

- **GIVEN** collector работает
- **WHEN** оператор подтверждает остановку
- **THEN** supervisor выполняет graceful shutdown
- **AND** панель остаётся доступной
- **AND** сохранённая active revision и ingestion-данные не удаляются

#### Scenario: Перезапуск сбора

- **GIVEN** collector работает с active revision
- **WHEN** оператор подтверждает перезапуск
- **THEN** выполняется graceful stop и новый запуск той же ревизии

### Requirement: Предсказуемое применение изменений

Система SHALL классифицировать изменение как применяемое без перезапуска, требующее перезапуска collector или требующее повторного запуска контейнерного стека.

#### Scenario: Draft сохранён без активации

- **GIVEN** оператор сохранил новый draft
- **WHEN** он не запускал проверку и активацию
- **THEN** работающий collector продолжает использовать прежнюю applied revision
- **AND** панель явно показывает неприменённые изменения

#### Scenario: Проверенная ревизия активирована

- **GIVEN** текущий draft прошёл обязательные проверки
- **WHEN** оператор активирует его для запуска
- **THEN** supervisor применяет ревизию через dynamic update либо контролируемый restart согласно изменённым полям
- **AND** отражает номер фактически applied revision

#### Scenario: Изменён инфраструктурный параметр контейнерного стека

- **GIVEN** сохранён параметр, который текущий процесс не может применить самостоятельно
- **WHEN** ревизия активируется
- **THEN** панель явно отмечает необходимость повторного запуска стека
- **AND** не сообщает об изменении как уже применённом

### Requirement: Ограниченная административная поверхность

Система SHALL NOT предоставлять web-процессу Docker socket, произвольное выполнение команд, чтение произвольных файлов или просмотр Telegram-содержимого.

#### Scenario: Оператор использует панель

- **GIVEN** оператор авторизован
- **WHEN** он работает со страницей настройки
- **THEN** доступны только операции с настройками, сессией и безопасным состоянием сервиса
- **AND** отсутствует интерфейс выполнения host-команд или просмотра собранных сообщений

### Requirement: Использование с телефона

Система SHALL предоставлять адаптивную HTML-страницу, пригодную для настройки с мобильного браузера без терминала.

#### Scenario: Страница открыта на узком экране

- **GIVEN** авторизованный оператор использует мобильный браузер
- **WHEN** открывается форма настроек
- **THEN** все разделы, ошибки валидации, кнопки сохранения и состояние применения доступны без горизонтальной прокрутки
