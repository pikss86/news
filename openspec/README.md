# OpenSpec в этом проекте

OpenSpec хранит проверяемые требования к поведению системы. Это не общий список идей и не
замена [ROADMAP.md](../ROADMAP.md).

## Структура

- `config.yaml` — постоянный контекст и правила подготовки изменений.
- `specs/<capability>/spec.md` — действующий контракт уже принятого поведения.
- `changes/<change>/proposal.md` — причина и границы одного активного изменения.
- `changes/<change>/design.md` — принятые технические решения.
- `changes/<change>/specs/` — delta к основным спецификациям.
- `changes/<change>/tasks.md` — реализация и проверка изменения.
- `changes/archive/` — принятые и архивированные изменения.

Новая идея сначала попадает в roadmap или обсуждение. После выбора ближайшей работы для неё
создаётся change. После реализации, проверки и приёмки delta-specs синхронизируются с `specs/`, а
change архивируется. Наличие файла в `changes/` не означает, что вся функция уже принята.

## Основные спецификации

| Capability | Ответственность |
| --- | --- |
| `raw-event-preservation` | Сохранение исходных TDLib-событий и точная дедупликация |
| `message-normalization` | Текущая нормализованная проекция сообщений и чатов |
| `message-versioning` | Неизменяемая история изменений и tombstones |
| `telegram-authorization` | Авторизация аккаунта и persistent TDLib session |
| `media-downloads` | Инвентаризация, очередь и состояние загрузки файлов |
| `collector-reliability` | Транзакционность, retry, graceful shutdown и наблюдаемость |

## Активные изменения

### `add-vpn-settings-ui`

Реализация панели настройки и управления в основном завершена. Автоматические проверки и
интеграционные сценарии отмечены в `tasks.md`. Незакрыт только пункт 7.8: полная ручная приёмка на
Linux-host с реальной Amnezia VPN и настоящим сценарием Telegram code/2FA. Пока этот результат не
зафиксирован, change нельзя считать полностью принятым и архивировать.

Read-only браузер собранных данных и последующие улучшения интерфейса описаны в
[README.md](../README.md). Перед существенным развитием этих возможностей для них следует создать
отдельную capability или OpenSpec change, чтобы эксплуатационная документация и технический
контракт снова совпадали.

## Проверка

```bash
openspec validate --all --strict
```

Проверка структуры не заменяет тесты реализации и ручные acceptance-сценарии, явно указанные в
`tasks.md`.
